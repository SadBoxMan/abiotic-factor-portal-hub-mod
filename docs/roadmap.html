1Prove custom world hooking is doableA hub portal that loads and enters a world from another pakDone▸

Where it stands

Proven with our own Test World: the hub spawned the world's loader, the level streamed in (found loaded and visible at once, ready after 0.2 s), the arrival pad appeared at the right spot, the hub portal switched on, and the return trip was wired back to the hub portal. The hub's LoadAsset lookup found the loader class.

What it took

  • The loader must be a Blueprint based on Epic's Level Instance actor with its Desired Runtime Behavior set to Standalone. A BeginPlay graph that calls Load Level Instance (by Name) did not work in this game.
  • The pak must be IoStore, and sit directly in Content\Paks.
2Create the test worldA tiny map and a loader Blueprint, packaged as a patch pakDone▸

Where it stands

The Test World is built, packaged and loads through the hub. The step-by-step walkthrough (see the walkthrough page) reflects the method that worked, including the Level Instance loader and the pitfalls hit on the way.

Watch-outs

  • Chunk label settings and the chunk id.
  • Engine assets are not part of your pak: copy the cube into your own folder.
  • The map must be listed under Packaging → maps to include, or it is not packaged.

If packaging fights back

  • Command-line package (RunUAT BuildCookRun) for clearer error messages.
  • UnrealPak on the cooked files directly, which is already in the tools folder.
Needs from you: about an hour in the editor on a first attempt, plus a slow first package.
3Hard-baked hub layouts for mod makersReady-to-upload hub setups that come with a world modPlanned▸

The idea

A world modder produces a bundle that already puts their portal in the hub. (My reading of the goal; worth confirming.)

Routes

  • A: Preset files. Each mod ships a small hub_preset.lua (slot, destination, look, light, world) that the hub merges. Needs a rule for two mods wanting one slot: first come, a priority number, or the player chooses.
  • B: An Export button in the editor. Writes a self-contained folder (hub, config, the modder's world entry) ready to zip. Easy to test, and it sits on top of A.
  • C: A runtime registration call other UE4SS mods use to add portals. Most flexible, but load order needs care.

Watch-outs

  • Slot conflicts between mods.
  • The DLC rule must still apply to baked layouts.
  • Clear naming so ids don't collide.

7A friendlier GUI that antivirus leaves alonePackage the editor for everyday usersPlanned▸

Routes

  • A: Keep the PowerShell script. Plain text, visible console, readable by anyone. Least suspicious form of script, though never zero-risk. Add a README note that it is plain, inspectable text.
  • B: A single-file web editor (HTML) in Edge or Chrome that reads and writes config.lua directly. No executable, no script, no install, so almost no antivirus risk. Needs a Chromium browser and a one-time file permission each session.
  • C: A compiled .exe (for example .NET). Looks polished, but unsigned executables are flagged far more often than scripts, and signing certificates cost money.
  • D: No external tool. Only presets and hand-editing.

Recommendation

B, keeping A as a fallback. B is a rebuild of the interface, so it is a real piece of work, but it removes the biggest worry.

8Condense into one modSeparate what is for function from what is for debuggingPlanned▸

The plan

  • Keep, for function: the hub mod and the editor.
  • Move out, for debugging: the logger, the material lab and the old proof of concept. Ship them as a separate dev/ folder, or fold the useful bits into the hub behind a debug = true switch.
  • Release shape: one PortalHub folder in the Mods folder, an optional tools folder, a version number and a changelog.

Watch-outs

UE4SS loads Lua modules slightly differently from a normal setup, so test the combined layout carefully, including hot reload.

9Annotated methodology walkthroughA detailed guide with sources from the Unreal Engine APIPlanned▸

What it is

A detailed walkthrough of the method the hub uses to load a custom world, with every step annotated and linked to Epic’s public Unreal Engine documentation (the API reference and the Blueprint node pages). A modder should be able to see not just what to do but why it works, and check each claim at its source.

What it would cover

  • The loader Blueprint, the level it streams, and how the hub spawns it, polls for the level and places the arrival pad.
  • Packaging as an IoStore patch pak: chunk ids, always-cook directories, which files to install and which never to.
  • An Advanced section for the small details modders trip over: transparency (Masked, not Translucent), bulk-setting materials, tiling and sub-region UVs, scrolling textures, lighting for a custom world, and a custom skybox.
  • What was tried and why it fails (for example calling the streaming functions from Lua, or a legacy pak), so nobody repeats it.

Watch-outs

Cite only public sources, mark what is inferred from testing rather than documented, and keep it in step with the walkthrough in item 2 once the method is settled.

How the pieces fit (decided 14 October 2026)

  • A world describes itself. The map maker sets the world's details in their own project, as variables on the loader Blueprint: title, type (vignette or home), lighting, arrival point, exit, and later music. The hub reads them; it does not have to be told.
  • The Portal Hub only connects worlds. Its job is putting each world's portal in the Portal Hub room. Its config shrinks to which world goes in which slot.
  • Some Lua is expected. Making a world behave like a vignette needs a small runtime script; the tutorial gives modders those tools, so a world can also be used without our hub.
  • Portal locations elsewhere in the Facility come much later. For now every world's portal goes in the Portal Hub room.

The plan before packaging

The project author's order, set on 14 October 2026. Each step is figured out before the next one starts. The notes in grey say where each one stands.

  1. Vignette confirmation: can we reliably set custom worlds as vignettes?
    Method found and the hub version passed in game on 14 Oct: the hub gives each world its own entry in the game's level table and marks the player as being in it (vignette check, Portal Entrance respawn, level name, title banner, fog gone). Still to do before moving on:
    • More level-name and vignette testing, with copies of the Test World under different names.
    • Make a custom world act exactly like a vignette does: clearing the weather, the proper world flags, the level name, and so on.
    • A custom title for the world (the one shown on entry).
    • World types, once the vignette tests pass on a few more worlds. The game has two, and modders pick one:
      • Vignette (V_): puzzle worlds and adventures. Equipment can't be used until the player reaches the world's exit, which is separate from its entrance; using the exit clears that restriction.
      • Home (H_, like Temple of Stone, Torii and the Cabin): player homes. No equipment restriction, and no separate exit.
      Found 14 Oct: both kinds hold the same Vignette_Zone, which gives the player Buff_InVignette. The equipment lock is Debuff_PortalSickness, applied only when the zone names a story flag (the Train's is TrainCompletedOnce; homes name none). How it works in the game: a vignette can have several exits but only one is the proper one; reaching it sets the flag, the sickness clears and never comes back for that world. Plan for custom vignettes: a completion flag per world, the zone pointed at it, and the world's proper exit setting it (WorldFlagSubsystem:SetWorldFlag). To check: flags are saved with the world, so what happens to a save if the world's mod is removed. The reward buff given on later uses of the proper exit is on the back burner.
  2. Lighting: how do we give the world custom lighting for days and nights? Dynamic lighting, like Stone Garden, and static lighting, like Albatross.
    A world can already borrow another area's lighting through the game's own system (Stone Garden's was shown in the Test World). Next: lighting of our own for day and night.
  3. Skyboxes: can we successfully make a skybox and relay that info to modders?
    Surveyed: the game's skies are dome meshes under /Game/Sky. Not started.
  4. Custom world music and ambient tracks (Stone Garden has its own music, for example).
    The game's lighting rows already carry music and ambient sound (MusicTracks, AmbientSoundTrack), so this likely builds on the lighting work.
  5. Custom exit for new worlds: a specific exit coordinate in the Facility, so a world can lead somewhere other than the portal room.
  6. Full tutorial: after vignette, skybox and lighting are all figured out, this can begin (it grows out of the walkthrough and the annotated guide, items 2 and 9).
    • A tutorial on writing the Lua for your own world by hand, for modders who don't want to use the GUI program.
  7. Mod packaging: package the mod, the program and everything else for Nexus Mods (items 6, 7 and 8 come in here).
    • Add the world settings (vignette or home, Leyak safety zone, title, and more as they are found) to the GUI.
    • Allow editing an existing world's settings through the GUI.
